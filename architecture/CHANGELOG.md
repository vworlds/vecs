# Changelog

All notable changes to the Vecs suite are documented here. Entries are grouped by
the Git release tags and each bullet is tagged with the owning subproject.

## Unreleased

- [vecs-physics] Fixed: `ContactEvents`, `SensorEvents`, and `HitEvents` opt-ins survive subtree moves and restores (#298, #309), including explicit component selection. Custom snapshots preserve presence only and restore fresh empty buffers, so reporting is re-armed without carrying source-world event references.
- [vecs-physics]: Release the Box2D world and move-export buffer through the engine singleton's remove hook on `World.dispose()` (#294, #295), including mid-tick disposal. Teardown hooks tolerate engine-first infrastructure removal; queued bodies, shapes, chains and joints are freed with the world. Reject a refused Box2D world at registration with an error naming the 128-live-world process limit instead of trapping or hanging on the next step. Live step/pose-out paths are unchanged.
- [vecs] Fixed: Whole-frame intervals no longer fire one frame late due to floating-point accumulation (#302, #303). Precompute a relative-tolerance threshold and clamp negative residue while preserving one fire per frame and positive backlog after large deltas.
- [vecs] [vecs-client]: `World.dispose()` now destroys infrastructure and singleton data after application cleanup (#296, #297), so module-owned resources can release through `remove` hooks. Inside a tick the final pass waits for `endFrame()`; outside a tick it follows the enclosing command drain or synchronous destroy-cascade cleanup. Component keys follow their carriers; if ordering stalls, an error names all registered survivors and their carriers instead of silently retaining them. Cycle breaking is deferred. `clearAllEntities()` retains its throwing behavior. This replaces the infrastructure-survives contract from #230; callers must discard the disposed world.
- [repo]: Add a REST-only worker CI wait with green/red/no-verdict exits, bounded Vecs failure digests, portable log reads with explicit request errors, and offline regression tests.
- [repo]: Port SpaceRocks' adaptive 10-second GraphQL watcher, Done-filtered board reads, per-repository archiving after merges, and opencode 2 HTTP worker launcher with permission/failure events.
- [repo]: Include tracked shell scripts in the root formatting checks and format pass.
- [repo]: Install a release benchmark base's own dependencies when its lockfile differs, and report base preparation/build failures as warnings.

## v1.0.51 (2026-10-10)

- [vecs-phaser] [vecs-phaser-server] [vecs-phaser-client]: **The dead-reckoning wire is incompatible with 1.0.50; upgrade server and client together.** `Motion` gains `rest: boolean`; `linearDamping`, `angularDamping`, `localCenterX`, `localCenterY`, `gravityScale` and `allowFastRotation` move to the new `MotionParams`. `phaserMotionComponents` is `[MotionClock, Motion, MotionParams]`, with `MotionParams` appended, and both `DeadReckonedModule`s require all three network components. `motionAtRest` is removed: the server decides rest and clients read `Motion.rest`. The integrator signatures are `motionStateFrom(motion, params, out)`, `stepMotion(state, params, clock)` and `motionPose(state, params, out)`. A `Motion` costs 26 bytes moving or 14 at rest with a frame below 128; `MotionParams` costs 1 byte for defaults or 21 with every group. An entity without it uses the exported, frozen `defaultMotionParams`. Moving baselines add or update f32-rounded constants only when they differ, in the same frame as `Motion`; rest baselines leave them untouched. Both peers copy the constants at a baseline using the exported `copyMotionParams(source, target)`, so stepping looks up no component.
- [vecs-protocol] [vecs-server] [vecs-client]: Whole-entity removals carry their server frame as resets, so an entity that leaves a view and returns, or a new entity under a reused id, is rebuilt without stale components or client-local state (#240, PR #242). **This wire layout is incompatible with 1.0.50; upgrade server and client together.** `StateDiff.resets` holds `[eid, frame]` pairs (`EntityReset`), or is `undefined` when the diff resets nothing; each occupies a removal entry in diff field 1, with the packed `ALL_COMPONENTS` id followed by `toFrame - frame` as a varint. Diffs without resets retain their encoding. History and client diff merging keep the newest reset and the snapshots and single-component removals that follow it, dropping state from before it. Resets apply only when newer than the rendered state at the start of the pull, including in held optimistic diffs, so overlapping deltas rebuild an entity once and interpolation never blends it from the entity it replaced. `ClientWorld` applies a frame in two `ON_LOAD` systems: `ClientWorld:Pull` handles server requests, pulls the diff and destroys reset entities; after the flush, `ClientWorld:Apply` applies snapshots and single-component removals. Direct `apply(now)` performs both outside a system or deferred scope. A malformed snapshot closes the client after preceding resets have applied. Reset-only frames count as content for history, redundancy and the ack-timeout probe.
- [vecs-server] [vecs-protocol]: The server's networked id quarantine is at least `historyFrames + 1` frames, 65 by default, or `networkEntityReuseWaitFrames` when larger (#240, PR #242). The option takes effect on the server's `entity` pool, which allocates all server entities, and must be a non-negative integer. The removal has left every session's history before the id is reused, so a client that has not acked it receives a baseline. A longer quarantine reuses ids later under churn. `ClientWorld` retains its zero-wait `network_entity` pool; do not pass the client-only `localEntityIdStart` to a server.
- [vecs-phaser-server] [vecs-server]: The server `DeadReckonedModule` requires `ServerWorldOptions.keepAliveFrames` and throws at install when unset. Set `keepAliveFrames: 1` on every server world that installs it: clients extrapolate at `ClientWorld.renderFrame`, which advances only as frames are applied, and need keepalives to keep drifting bodies moving in an idle scene.
- [vecs-protocol] [vecs-server] [vecs-client]: Added opt-in `ServerWorldOptions.redundancyFrames`, an integer `R` of at least 1 and less than `historyFrames`. A healthy session sends deltas from `max(ack, base)`, where `base` is the state frame of the send `R` sends ago: the newest frame at which replicated state changed as of that baseline, content delta or keepalive. A change has up to `R` consecutive send opportunities regardless of ack lag or sparse traffic; an ack can stop repetition sooner, later values can supersede earlier ones, and fallback can send more copies. With in-order delivery (or after dependencies arrive), up to `R - 1` lost sends carrying a change are absorbed; reordering can hold a marked diff with no loss. Lost keepalives or repeats do not advance the base past state the client holds. `Server2Client.optimistic` (bare tag 6) marks a base past the ack; the client holds up to 8 such diffs until applicable and reports an unresolved `Client2Server.gap` (bare tag 7). An unacked content probe triggers fallback after twice the smoothed ack round trip (at least 100 ms); an ack covering that probe retargets it to the newest sent content still above the ack and restarts the timer. A gap or overdue probe starts deltas from the ack until caught up; if required history has been evicted, the server sends a baseline. The stall costs about one round trip, partly hidden by interpolation. Baselines and resynchronization never run ahead of the ack. Unset, the option leaves replication unchanged. See [Replication](REPLICATION.md).
- [vecs-server] [vecs-client]: Added opt-in `ServerWorldOptions.keepAliveFrames`, exposed as `ServerWorld.keepAliveFrames`: an integer `K` of at least 1. A session with an acked baseline that has not been sent a diff for `K` frames receives an empty diff, applied and acked normally. It uses the ordinary ack or optimistic base and counts as a redundancy send with the last change's state frame, but not as content for the ack-timeout probe. No keepalive is sent while a baseline is in flight or needed; RPC-only traffic without a diff does not restart the count. Unset, replication is unchanged. A keepalive costs 5–11 payload bytes as frame numbers grow, plus 1 when optimistic; at 30 Hz that is 150–330 B/s for `K = 1`, excluding transport and ACK overhead. `1` is the safe value for a continuously advancing render frame; larger values save bytes but let it wait between frames. See [The keepalive](REPLICATION.md#the-keepalive).
- [vecs-phaser-server] [vecs-phaser-client] [vecs-phaser]: `DeadReckoned` can be added or removed at runtime. Adding it removes the streamed render pose and writes the first `Motion` baseline in the same frame; removing it removes `Motion`, `MotionParams` and the server-local prediction and restores the physics pose as render `Position` and `Rotation` in that frame. Deferred switches complete through the pose guard using the entity's final state, so toggling both ways in one flush is supported; completed dead-reckoned entities carry no render pose and reject one being added. Clients keep their render pose and blend both hand-offs using `blendMs` and the existing snap limits. The hand-off owns its output pose instances and treats replication-owned instances, including interpolation history, as read-only; the dead-reckoned-to-streamed offset fades before the track is dropped. `blendMs: 0` disables blending and snaps every correction. Switching to dead reckoning can hold the last streamed pose for about one server frame before the baseline, then blend to catch up. Switch on state changes, such as drifting versus being driven by forces or joints.
- [vecs-client]: A network removal of a plain component is skipped while a component that survives the diff brings it through `With`; a bringer set by the same diff counts if it remains present after that diff. This keeps client-local render `Position` and `Rotation` present during a switch to `Motion`, without `remove`/`add` hooks or `DrawBy` children exiting and re-entering. Whole-entity resets still destroy every component, relationship removals apply as sent, and removing a bringer does not remove its companions. See [Applying a frame](../lib/vecs-client/docs/client-world.md#applying-a-frame).
- [vecs-phaser-server]: The pose guard runs after `ON_STORE` and before the server records the frame. `phaser.guard.pose` copies a newly paired physics pose into changed render components, and `phaser.guard.motion` primes every first dead-reckoning baseline, so entities created or switched after `POST_UPDATE`, including in `PRE_STORE`, `ON_STORE` or RPC handlers, reach the wire at their physics pose. A body without a Box2D body yet receives a rest baseline corrected by its first physics step.
- [vecs-phaser-client]: Added the Phaser-free `@vworlds/vecs-phaser-client/headless` entry for Node clients (#243), exporting `DeadReckonedModule`, `DeadReckonedModuleConfig`, `phaserInterpolators` and `rotationInterpolator`. The browser entry retains these exports, and publish preparation preserves subpaths with dist-root targets.
- [vecs-phaser-server] [vecs-phaser-client] [vecs-phaser]: Rest baselines hold exactly their encoded `x`, `y` and `angle` on both peers, bypassing the integrator's center-of-mass and angle round trip. The server sets `Motion.rest` for a sleeping body, an entity without a body, or a body with no velocity and nothing accelerating it. `MotionParams` writes complete before their announcement, including outside deferred mode.
- [vecs-server]: A same-frame view exit and re-entry of the same entity is cancelled, and its changes are sent as ordinary deltas instead of full snapshots (#239). This also preserves an entity that loses and regains `Networked` in one frame while still sending its component removals. An exit in one frame and entry in a later frame sends a reset followed by a full snapshot.
- [vecs]: The published manifest no longer carries a `lint-staged` config. Repository commits use the root config, which retains the same TypeScript formatting/linting and Markdown formatting commands.

## v1.0.50 (2026-10-08)

- [vecs]: Added `World.dispose()`, which ends a world's life by destroying every entity the application and its modules created (#230). Each entity goes through the ordinary destroy path, so every `remove` hook fires once, cleanup policies and `ChildOf` / `OwnedTarget` cascades run as usual, and an entity a cascade or a hook already destroyed is skipped. The infrastructure stays, with the data on it: component and module entities (every `Component`), the entities behind queries and systems (the `Query` component) and phase entities (the `Phase` component). An entity used as a component key is destroyed after every entity that carries it; the order among the rest is unspecified. Pending commands are neither flushed early nor discarded: they run first and the destruction follows in the same queue, so a call from a system, a hook or a `defer` block completes when that queue drains. The call is idempotent, also when a hook re-enters it, and a disposed world must not be used again, which nothing enforces so that no hot path pays for a check. Previously the only whole-world teardown was `clearAllEntities()`, which also destroys the component, module, query, system and phase entities and throws while a component entity is still in use, so an application finished with a world could not release the resources of its entities and keep the world's own entities intact.
- [vecs-client]: `ClientWorld.dispose()` now destroys the client-local entities too, through `World.dispose()` after the replicated ones and once the socket is closed (#230). Their components' `remove` hooks run, so the render resources they own, such as the Phaser GameObjects of UI, effects and `DrawBy` children, are released the same way as the replicated ones, and an application no longer needs its own sweep of local entities when it switches worlds. The client's own component, query and system entities stay. Previously `dispose()` destroyed only the replicated (`Networked`) entities, so client-local entities, and the resources their `remove` hooks would have released, outlived the world. It also works while the world is deferred, such as in a `disconnect` handler that `apply()` triggers by closing the client for a protocol error: the destruction completes when the running system finishes.
- [vecs-physics]: Destroying either body of a joint now destroys the joint entity along with it, as the `JointBodyA` and `JointBodyB` JSDoc promised (#229). `JointsModule` registers both body relationships with `onDeleteTarget = CleanupPolicy.Delete`, so the joint entity and every component a game attached to it go in the same cascade, the other body is only released from the constraint, and a body that several joints connect to takes all of them. Box2D needs no extra guard: the joint's exit queues its handle for `PhysicsReaper`, which destroys joints before bodies, so no joint is destroyed twice. Removing `Body` from a connected body, or pointing a slot at another body, still leaves the joint entity alone. A game that relied on the joint entity surviving, to reconnect it to another body, must now re-point the slot before it destroys the old body. Previously both relationships kept the default `CleanupPolicy.Remove`, so destroying a body only dropped the edge and left a bodiless joint entity alive with whatever state was attached to it, and every game had to cascade joint cleanup by hand, for example with `ChildOf` and `OwnedTarget`, or leak joint entities.
- [vecs-phaser-server] [vecs-phaser-client] [vecs-phaser]: Added dead reckoning (#217): a body tagged `DeadReckoned` sends its pose as an occasional `Motion` baseline that clients extrapolate, instead of streaming every change of its render pose. On the server, `DeadReckonedModule` (options `positionTolerance`, default 0.01 m, `angleTolerance`, default 0.01 rad, and `maxBaselineAge`, default 30 s, `0` to disable) requires a `ServerWorld` whose network components include `phaserMotionComponents`, installs `PhaserServerModule`, and creates the world's single `Networked` `MotionClock` entity from the physics settings, gravity included; adding `MotionClock` to any other entity throws, and every `View` must see that entity. The `DeadReckoned` tag is structural and decided at spawn: through `With` it brings `Motion`, the physics `Rotation` and a server-local prediction (never replicated, never captured in a subtree snapshot), its `add` hook removes the render `Position` and `Rotation`, and adding a render pose to a dead-reckoned entity throws; removing the tag at runtime is not supported. The streamed `phaser.sync.position` / `phaser.sync.rotation` systems are unchanged, and a new `POST_UPDATE` system, `phaser.sync.motion` (`.with(PhysicsPosition, PhysicsRotation, DeadReckoned, Motion, …)`), steps the clients' prediction once per physics step from the baseline exactly as the wire carries it (every field written as an f32), compares it with the physics pose, and writes a new baseline in place, announced with `modified`, when the position or angle strays past its tolerance, when the body falls asleep (a baseline at rest: zero velocities, gravity scale 0), or when a moving baseline outlives `maxBaselineAge`, which bounds the steps a client runs to catch up a body it has just started to see. A baseline holds the physics pose, Box2D's velocities, damping, center of mass, effective gravity scale (0 for a body without mass) and `allowFastRotation`, and is stamped with `ServerWorld.frame`. Per body per step the system allocates nothing, asks Box2D whether the body is awake only when its pose did not change, reads the rest only when it writes a baseline, and only compares the pose of a body at rest. A body moved to another world by `moveSubtree` keeps `DeadReckoned` and gets a fresh baseline at the destination's frame on its first step there. On the client, `DeadReckonedModule` (options `blendMs`, default 100, `snapDistance`, default 1 m, `snapAngle`, default 0.5 rad) requires a `ClientWorld` with the same components; `Motion` brings a client-local `Position` and `Rotation`, and the `POST_LOAD` system `phaser.extrapolate.motion` samples each baseline at `ClientWorld.renderFrame`, stepping `floor(renderFrame − Motion.frame)` steps and interpolating the fraction, writes the pose in place only when it changed, ignores a baseline older than the one it holds, applies a correction received in time at once, and blends a late one out over `blendMs` unless it exceeds a snap limit. Running right after `ClientWorld.apply`, it puts the extrapolated pose in front of gameplay systems, `phaser.resolve.offset` and the render sync in the same frame, as an interpolated pose is, whatever order the modules are installed in, so a `DrawBy` child of a dead-reckoned body does not lag. `@vworlds/vecs-phaser` adds `motionAtRest(motion, clock)`, which both sides use to skip stepping a baseline that holds its body still. Measured with the replication harness: 200 drifting bodies cost 600 B/s per client dead reckoned against 102 KB/s streamed; at 200 ms round trip, 5% loss each way and reordering for 60 s, the rendered pose stayed within 7.1 mm and 2.1e-3 rad of the server's outside the 150 ms after each correction, with no resync or protocol error. See [Dead reckoning](../lib/vecs-phaser-server/README.md#dead-reckoning).
- [vecs-physics]: `PhysicsQueries` gains three reads for predicting a body: `settings()` returns the frozen `PhysicsSettings` the world was built with (`gravity`, `fixedTimeStep`, `subSteps`, `maximumLinearSpeed`), `isAwake(entity)` reports whether an entity's body is awake without allocating, and `bodyMotion(entity, out)` fills a reusable `BodyMotion` with `awake`, the velocities, damping, local center of mass, `allowFastRotation` and the gravity scale Box2D applies (0 for a body without mass), returning `false` for an entity without a live body. `BodyMotion` and `PhysicsSettings` are exported. See [Queries](../lib/vecs-physics/docs/queries.md#settings-and-body-motion).
- [vecs-server]: Added `ServerWorld.frame`, the frame the next `send()` numbers: during `progress()`, the frame the tick in flight reaches clients as. Dead reckoning stamps its baselines with it.
- [vecs-phaser]: Added the dead-reckoning wire components and the shared integrator (#217), the groundwork for extrapolating physics bodies on the client instead of streaming their pose every tick. `Motion` is a complete baseline: `frame` (varint u32), the body origin `x`, `y`, `angle` and the velocities `vx`, `vy`, `w` (f32), then a one-byte mask and the groups it lists: `linearDamping`/`angularDamping` (bit 0) and `localCenterX`/`localCenterY` (bit 1), each present when either of its fields is non-zero, `gravityScale` (bit 2) when it is not 1, and the `allowFastRotation` flag (bit 3, no payload). Its hand-written codec costs 26 bytes with a frame below 128, plus 8 per pair and 4 for the gravity scale, and absent groups decode to their defaults. `MotionClock` (`stepSeconds`, `subSteps`, `gravityX`, `gravityY`, `maxLinearSpeed`) carries the world's physics constants on one entity. Neither is in `phaserNetworkComponents`, whose order is the protocol; an application appends the new `phaserMotionComponents` (`MotionClock`, then `Motion`) to its own network components, so no wire id shifts. `motionStateFrom`, `stepMotion` and `motionPose` (with `MotionState` and `MotionPose`) predict a body from its baseline by mirroring Box2D v3's free-body step at commit 3a4f0da (also retained by the owned 6.0.1 package): the `1/(1 + h·c)` damping, gravity times the body's gravity scale, the linear speed clamp and the per-step angular one unless `allowFastRotation` is set, `b2IntegrateRotation` per substep, then `b2MulRot`, `b2NormalizeRot` and the origin `c − R(q)·localCenter`, with the angle by Box2D's `b2Atan2`. The stepping operations use f32 arithmetic; `motionStateFrom` initializes arbitrary rotations with `sin`/`cos`, so the numerical evidence is real-WASM accuracy on the tested runtime, not cross-browser bitwise proof. A baseline taken from a physics `Rotation` stays within 8e-5 m and 2.5e-5 rad in those tested cases. The baseline carries no mass, so a sender sets `gravityScale` to 0 for a kinematic body, to which Box2D applies no gravity. Forces, contacts, joints, locked axes and sleep are not modeled. The server and client modules that use them follow in a later change.
- [vecs-client]: Added `ClientWorld.renderFrame`, backed by the new `DiffBuffer.renderFrame`: the fractional server frame the client renders, the point its interpolators sample (#217). While the buffer blends from frame N toward N + 1 with blend factor `alpha` it is `N + alpha`, and it is kept whether or not interpolators are registered. It is `0` until the first baseline is applied, goes back to `0` when a baseline resets the world and then to the baseline's frame, is `0` after `dispose()`, never decreases otherwise, and never passes the newest frame received: when the buffer runs dry it holds at the newest frame applied. Dead reckoning will extrapolate on it, so extrapolated and interpolated entities show the same moment.

## v1.0.49 (2026-10-07)

- [vecs-phaser] [vecs-phaser-client]: Added the `InheritRotation` tag (an `angle` field, exported from `@vworlds/vecs-phaser`) so a `DrawBy` child can follow its parent's rotation. On a tagged child, `phaser.resolve.offset` works in the parent's local frame, in the same pass that resolves `Position`: with `a` the parent's interpolated `Rotation.angle` (`0` when the parent has none, or its derived world angle when the parent is tagged too), the child's `Position` is the parent's `Position` plus its `Offset` rotated by `a`, and its `Rotation` is `a` plus the tag's `angle`. Position and rotation stay in lockstep on every frame, interpolated ones included, and a chain of tagged and untagged children resolves parent-first within one frame. The tag adds a client-local `Rotation` (a `With` companion, as `DrawBy` adds `Position`) that holds the derived angle and is overwritten every frame, so writing or replicating `Rotation` on a tagged child has no effect. Removing the tag from a `DrawBy` child returns it to its own rotation: its `Rotation` becomes the tag's `angle` and its offset is no longer rotated. The tag does nothing without `DrawBy`, so removing it from an entity that has none leaves that entity's `Rotation` alone, and a child whose `DrawBy` is removed (for example because its parent was destroyed) keeps its last pose. `InheritRotation` is a wire type but is not part of `phaserNetworkComponents`: that list's order is the protocol, and appending to it would shift the wire id of every application component listed after it. It is client-local by default; an application that wants the server to set it lists it in its own network components, after its existing ones, on the server and the client alike. Untagged `DrawBy` children resolve exactly as before. The `DrawBy` and `Offset` JSDoc wrongly said the offset was rotated by the parent's `Rotation`; they now say it is added as is unless the child is tagged. Previously a `DrawBy` child could not follow its parent's rotation: the resolver added the `Offset` to the parent's `Position` as is and the child's own `Rotation` stayed independent, so a crack, decal or label drawn on a spinning parent needed a per-frame game-side mirror of the parent's rotation (#218).
- [vecs-phaser-server]: `phaser.sync.position` and `phaser.sync.rotation` now inject the render component and write a changed pose into it in place, announced with `entity.modified(...)`, instead of reading it with `entity.get` and calling `entity.set` with a new props object. Their query guarantees the render component exists, so the `undefined` check is gone, and injection resolves the component once when the callback is registered instead of on every call. `modified` and `set` share the notification that follows the write, so the `set` hooks, the `update` routing to watching systems and the `ServerWorld` replication of the render pose are unchanged; only the cost differs, because a write no longer allocates a props literal or copies it at flush (about 60 ns and 49 bytes less per changed write in a 1000-entity micro-benchmark). One edge now behaves better: when a sync system drains two events for the same entity in one inbox window, for example an entity that enters and has its physics pose modified before the system runs, the second finds the first's write already applied, so the render pose is modified once instead of twice. The design guide's Injection section and `.agents/rules/design.md` now state the rule that a system callback injects every component it always uses and keeps `entity.get` for a component that is conditionally needed and rarely required, and the guide's `PhaserServerModule` and reactive-sync snippets show the injected form.
- [vecs-physics]: A zero `Force`, `Torque`, `Impulse` or `AngularImpulse` no longer wakes a sleeping body, whatever its `wake` flag says (#215). `PhysicsForceGather` skips a `Force` with `x === 0 && y === 0` and a `Torque` with `value === 0` without calling Box2D, so an idle thrust component no longer keeps its body awake and no longer costs a wasm call every step. `PhysicsImpulseAccumulate` ignores a zero `Impulse` or `AngularImpulse` when it is set (it is not accumulated and its `wake` does not count) and skips a sum that is exactly zero when it applies impulses, so impulses that cancel out do not wake the body either. Non-zero loads are unchanged: `wake: true` still wakes a sleeping body and `wake: false` still leaves it asleep. To wake a body or keep it awake, use the `Sleep` component (`awake: true` wakes it, `enabled: false` stops it sleeping). Previously every `Force`, `Torque`, `Impulse` and `AngularImpulse` with `wake: true` woke a sleeping body whatever its magnitude, so a persistent `Force { x: 0, y: 0 }`, such as a thrust component written back to zero when the player lets go, never let its body stay asleep: its pose was replicated every tick and it stayed in the solver. See `lib/vecs-physics/docs/forces-and-impulses.md`.
- [vecs-server]: A session is no longer sent a full baseline on every frame once its client's acks lag by a few frames, which any round trip above roughly 130 ms causes, nor one every few frames while its view is quiet (#216). `ServerWorldOptions.historyFrames` sets how many frames of history each session keeps (default 64, about two seconds at 30 Hz; an integer of at least 2, which the constructor enforces). The default is long because a baseline holds state back for a round trip, so the ack lag peaks at twice its steady size right after one; a slot holds references to already-encoded snapshots, so the window costs little. A client is served a delta while nothing it is missing has left that history: `History` remembers the newest frame that left the window holding a snapshot or a removal, a session needs a baseline only when its ack is older than that frame, and a frame that left empty took nothing with it. So a view that stays quiet is never resynced however old the client's ack grows, and when it changes the delta is labelled with the ack the client really holds (`History.pull` accepts an ack older than the window and merges only the frames still in it); changes further apart than the window need no baseline either. A new session, or one that has lost a frame with content, is sent a baseline once and then no more state until the client acks it: only an ack of the baseline's frame or a later one releases deltas, RPC traffic keeps flowing in frames that carry no state, and the history keeps recording so the first delta after the ack carries everything that changed. A baseline is sent again only when it is presumed lost: after twice the session's smoothed ack round trip (an average that moves an eighth of the way to each sample, the time from sending a frame to receiving its ack, measured over the last 256 frames whatever the window) and at least 100 ms, or after one second, the initial retransmission timeout of RFC 6298, before the first sample. There is no backoff: while only the acks are missing, the client rebuilds once per presumption interval, which is the price of recovering a lost baseline soon. A baseline that would be empty is not sent to a client that has never acked one, which holds nothing, but it is sent to one that has, because rebuilding from nothing is what clears the entities that left its view while it stalled. `needsFullSnapshot` and `needsResync` become one `needsBaseline` flag, since every baseline now re-sends the whole view, and the session tracks the baseline in flight with `resyncFrame` and `resyncSentAtMs` instead of comparing acks with the frame the session was created on. A baseline is still destroy-and-rebuild on the client, but it now arrives at connect and after a real stall instead of continuously. See [Sessions](../lib/vecs-server/docs/sessions.md#deltas-baselines-and-the-history-window). Previously every session kept 5 frames of history (about 167 ms at 30 Hz) and was resynced whenever its ack was more than 5 frames old, and the baseline flags cleared on any ack newer than the frame the session was created on, so a client whose ack lagged by more than 5 frames was sent a full baseline on every frame, a new session was sent one on every frame of its first round trip, and a session with nothing to send, which is sent no frame and so never advances its ack, was sent one every 6 frames. The client destroyed and recreated every replicated entity for each of them, so a player at a 200 ms round trip had the world rebuilt on nearly every frame.
- [vecs-client]: `DiffBuffer` no longer lets a stale diff roll the client back (#216). Once the buffer has drained, a diff for a frame the client already has, a datagram the unordered channel delivered late or twice, is discarded instead of becoming the new starting point, and a diff that starts past the client's frame is rejected as it already was while frames were buffered; only after `reset()` does any diff start the stream. Previously a straggler arriving after the buffer drained set the acked frame back, the next delta, which starts at the frame the server last saw acked, then started past the client's frame, and the client closed with a protocol error, the close #213 added. Frames delayed by a retransmission timeout, hundreds of milliseconds behind their successors, caused it within seconds to tens of seconds on a lossy link; the server's old habit of resending a full baseline every frame had hidden it.
- [vecs-physics] [vecs-phaser-server]: `PhysicsPoseSyncOut` and the `phaser.sync.position` / `phaser.sync.rotation` systems now write a pose component only when its value changed (#214). The physics writer compares `Position`, `Rotation`, `LinearVelocity` and `AngularVelocity` with the simulated values field by field, using exact `!==` with no epsilon because Box2D returns bit-identical values for a body that did not move or turn, and calls `set` only when a field differs. The render sync skips its write when the render `Position` or `Rotation` already holds the physics value, on entry as well as on update. A body flying in a straight line no longer modifies, and so no longer replicates, its constant `Rotation` and `AngularVelocity`; an awake body at rest modifies and replicates nothing; a body that moves and turns still gets exactly one modification per changed component per step. `entity.set` is unchanged and still always marks a component modified, so game code can still poke reactive systems with an equal value. What changes is that `set` hooks and `update` systems on the physics pose components, and on the render pose they feed, now run when the pose changed instead of on every step of every awake body, so a system that must visit every body on every step should iterate with `each`, which visits asleep bodies too. Previously both writers called `set` on every moved body every step whether or not the value changed, so every awake body fired `onSet`, routed `update` events to every watching system and, for the networked render pose, recorded a snapshot every frame: a bullet's constant `Rotation` alone cost 886 B/s per client.
- [vecs-client]: `ClientWorld` now ignores the frames that arrive on a socket `attachSocket` has replaced, by the rule it already applied to that socket's `disconnect` events and rejected sends, so the documented "late events from the previous socket are ignored" holds for frames too. Previously the receive handler was not told which socket a frame came from and treated every frame as the current connection's: a straggler on the old socket could push an old server session's diff into the new session's buffer, where it was applied and acked, a retransmitted close notice disconnected the new connection with the old session's reason, and an undecodable frame closed the new connection.
- [vecs-protocol] [vecs-server] [vecs-client]: A frame that cannot be decoded now closes the connection it came from instead of throwing into the transport. `@vworlds/vecs-protocol` exports a new reserved close code, `CLOSE_PROTOCOL_ERROR_CODE` (`1`; codes `0`–`100` stay reserved for the protocol), which `@vworlds/vecs-client` and `@vworlds/vecs-server` re-export next to `RPC_CLOSED_CODE` and `RPC_TIMEOUT_CODE`. `ServerWorld` decodes each inbound frame inside a guard: a truncated frame, random bytes or an unknown field tag (for example from a client on a newer protocol version) is dropped and only that session is closed, gracefully, through `closeSession` with `CLOSE_PROTOCOL_ERROR_CODE` and the reason `protocol error: <decoder message>`. `NetworkClient.closeReason` records it, the client receives it on the close frame, and the existing linger and exactly-once teardown run; a session that is already closing keeps its own reason, and other sessions are untouched. `ClientWorld` does the same for a frame that fails to decode, a snapshot whose envelope cannot be read, a diff the diff buffer rejects because it starts after the last frame the client acknowledged, and a snapshot that fails to decode when `apply()` applies it (an unregistered wire type from a newer server, a malformed payload, or an `Exclusive` relationship snapshot with several targets). It closes through `close()`, so `disconnect` fires once with `{ code: CLOSE_PROTOCOL_ERROR_CODE, reason: "protocol error: …" }`, pending calls reject with `RPC_CLOSED_CODE`, the socket closes and the replicated entities stay in place, and `apply()` returns without applying the remaining snapshots or the removals of that diff. A baseline is read before anything is torn down, so a malformed one leaves the replicated entities in place and fires no `reset`. Exceptions thrown by application code (an `on("set")` hook while a valid snapshot is applied, a `reset` handler, an `on("remove")` hook while a baseline destroys the replicated entities) still propagate and do not disconnect the client, and a payload that fails to decode inside the diff buffer's interpolation of components that have an interpolator still throws out of `apply()`. Previously a truncated frame, random bytes or an unknown field tag from a single client threw out of the socket's `receive` handler, which with `@vworlds/dgram-server` is an uncaught exception in the server process instead of the loss of that client's own session (vworlds/vecs#211); on the client the same frame, a malformed snapshot envelope and an out-of-order diff threw into the transport, an undecodable snapshot threw out of `apply()` and so out of `progress()`, and a malformed baseline had already destroyed the replicated entities when it failed.
- [vecs-protocol] [vecs-server] [vecs-client]: `RPC_UNSPECIFIED_ERROR_CODE` (`1`) is now exported from `@vworlds/vecs-protocol`, as `rpc.md` and the v1.0.46 entry already documented it, and `@vworlds/vecs-server` and `@vworlds/vecs-client` re-export it next to `RPC_CLOSED_CODE` and `RPC_TIMEOUT_CODE`. A caller can compare an `RPCError`'s `code` against it to recognize a call that failed without an application code: its handler threw a value with no usable code, such as a plain `Error`, or the request named an rpc id with no handler. Previously only `RPC_TIMEOUT_CODE` and `RPC_CLOSED_CODE` were exported.
- [vecs-protocol] [vecs-server] [vecs-client]: An RPC handler now runs once per call however often the caller retransmits its request, and a cached reply is dropped when the caller acknowledges it instead of living as long as the session. `SessionRPC` tracks the calls whose handler is still running and ignores further copies of them, including two copies in one `process()` batch; the reply goes out once when the handler settles, and a later copy gets that cached reply. Each side publishes a low watermark, `SessionRPC.settledBelow` (the lowest call id it still waits on, or its next call id when none is pending), in a new field `rpcSettledBelow` of `Client2Server` and `Server2Client`, and the receiver passes it to the new `SessionRPC.setPeerSettledBelow(value)`. That call only moves forward, drops the cached and unsent replies below the watermark, and makes the channel ignore requests below it as stale copies of calls the caller already settled; a handler still running for such a call has its reply discarded. `ClientWorld` and `ServerWorld` do this on every frame. The field is tag 5 followed by a `u32` and is absent when `0`, so a frame from a peer that never made a call, or whose first call has not settled, is byte-identical to before. Older decoders reject the new tag, and a client sends it once its first call has settled, so deploy servers before clients: a new server reads frames from old and new clients alike, but an older server throws on a new client's frame, and `ServerWorld` does not catch decode errors (#211). `SessionRPC.abortPending` now also forgets the peer (the watermark returns to `0`, the cached replies and in-flight tracking are cleared, and the replies of handlers still running are discarded), because `ClientWorld` reuses its channel across reconnects and a new server session numbers its calls from `0` again. Code that drives a bare `SessionRPC` must now pass `settledBelow` to the peer's `setPeerSettledBelow` with every frame: `timeoutTick` no longer ages cached replies, so without the watermark they are never evicted. Previously a handler that took longer than one ack interval ran again for every retransmitted copy until its first run finished, so a non-idempotent handler applied its side effects several times, and on the client every copy that arrived between two `apply()` calls ran the handler; and cached replies were evicted only by `timeoutTick`, which nothing in the monorepo called, so every reply stayed cached for the session's lifetime (#208).

## v1.0.48 (2026-10-06)

- [vecs-client]: `ClientWorld.invoke()` now settles as soon as its reply arrives, instead of when `apply()` next runs. `ClientWorld` hands reply messages to its RPC channel as it receives the frame, ahead of the frame's state diff and close notice, so an application can await a call (for example `auth` right after connecting) while nothing ticks the world, and a reply that shares a frame with a close notice still settles with the server's result before the disconnect aborts the remaining calls. Once its reply has arrived, the request also stops being retransmitted with the acks. Requests the server makes on the client are unchanged: their `listen` handlers still run from `apply()`, in the world's `ON_LOAD` phase. A reply settles its call and nothing more: the state the server sent in the same frame is applied later by `apply()`, possibly after interpolation delay, so callers must not assume a reply's side effects are already visible in the world when the promise resolves. Because replies no longer wait in a queue, a disconnect has no queued replies left to settle, and `dispose()` no longer abandons a reply: a call whose reply has arrived has already resolved and is not rejected with `RPC_CLOSED_CODE`. Previously every incoming RPC message waited in an inbox for `apply()`, so awaiting a call while nothing applied the world never settled, and until `apply()` ran the client kept retransmitting the request with every ack while the server kept re-sending its cached reply.
- [vecs-phaser] [vecs-phaser-client]: Added the `OpenPath` tag (protocol type 23) for open strokes. An `Arc` with `OpenPath` strokes as an open arc instead of closing with a chord between its ends, so progress rings and cooldown arcs no longer need client code that reaches into Phaser, and a `Polygon` with it strokes as a polyline. The client calls `setClosePath(false)` while the tag is present and `setClosePath(true)` once it is removed. Other renderables ignore it, since Phaser's Canvas renderer always closes the stroke of an `Ellipse`, `Rectangle`, `Star` or `Triangle` and the rest have no outline to close, and fills are unchanged. The tag encodes to zero bytes, but appending it to `phaserNetworkComponents` shifts the wire ids of application components listed after it, and older clients reject frames that carry it, so upgrade server and client together.

- [vecs]: Added the `OneOf` pair trait: `world.component(R).add(OneOf, parent)` requires every `R` target to be a direct `ChildOf` child of `parent`, so adding any other target throws. Point it at the relationship's own component entity for enum-style values. Declare it before `R` is in use; it cannot be removed. See [Relationships](../lib/vecs/docs/relationships.md#oneof-target-constraint).
- [vecs]: `Entity.add` / `Entity.remove` (and `Query.add` / `Query.remove`) accept any `ComponentRef` as a relationship target: an entity, a registered class or an eid. The target is resolved eagerly with `world.entity(target)`, so a target that does not exist throws at the call site, even in deferred mode. `World.getEntity` now throws for an `Entity` from another world instead of returning `undefined`; unknown ids from the same world still return `undefined`.
- [vecs]: Target injection can project the target entity itself: `{ target: [R, Entity] }` injects the target, `{ target: [R, C] }` injects one target component without wrapping it in a tuple, and `{ target: [R, [Entity, C, ...]] }` injects several values in order.
- [vecs]: `OwnedTarget` and `Traversable` are now irrevocable: removing either trait from a relationship, or swapping it with `attach`, throws instead of tearing down its policy. World teardown (`clearAllEntities`, entity destruction) is exempt.
- [vecs]: Trait invariants (`Exclusive`, `OwnedTarget`, `Traversable`) are now checked when the trait change is applied rather than when it is called, so an invalid trait change made in deferred mode throws at flush instead of being queued silently. The check runs after the trait is stored, so the throw leaves the world partial, like any other throw during a mutation cascade.
- [vecs]: Destroying a component entity now applies its `onDelete` policy by walking that component's carriers instead of scanning the whole world twice. A `CleanupPolicy.Throw` component entity that is still in use and is reached during a deferred drain or a relationship cascade now throws instead of silently aborting, and the world must be discarded. A synchronous `destroy()` still throws before mutating anything, so the world stays usable.
- [vecs]: Less allocation on teardown and grouping. Entity destruction and cascade cleanup iterate with `forEachSafe` instead of snapshot copies (`IterableArrayMap.forEachSafe` is new public API: it visits every entry while the callback deletes the current one), relationship teardown no longer copies its target list, a component keeps its carrier set for reuse, and `groupBy` re-keying no longer allocates a `Set` when an entity has zero or one key (the exclusive-relationship case).
- [repo]: Added `bench/sector-tick.ts`, a deterministic headless benchmark of a multi-world game server tick (physics-like pose sync, reactive and `.each` systems, exclusive relationship retargeting, entity churn, and `ServerWorld` diff recording with an in-memory client). It runs against the built `dist` packages (`npm run bench:sector`), fingerprints the final state, callback order and network bytes, and `bench/compare.ts` runs interleaved A/B comparisons between two builds. See [Benchmarks](../bench/README.md).
- [vecs]: Faster component updates: `all` and `any` query terms no longer re-evaluate their membership on every data-only change of a child component. Their membership depends only on their children's membership, which still reaches them as enter/exit events, so the re-evaluation could not change anything unless an event was still being delivered; that re-entrant case (inline mutation from a query callback) keeps the previous behavior. About 10% off the sector-tick benchmark's mean tick, with identical callback order and network output.
- [vecs]: Faster `modified` routing: the world indexes built queries by the component eids they watch for updates, and an update is delivered by walking that index instead of every update-watching query the entity belongs to. The index is used when every watcher of the component is a system, whose delivery only queues inbox events; when a plain or grouped query watches it, routing walks the entity's membership in insertion order exactly as before. About 15% off the sector-tick benchmark's mean tick, with identical callback order and network output.
- [vecs]: Faster `IterableArrayMap`, which backs every entity's component storage and the world's entity table: lookups read a small-integer slot array and a dense value array instead of an index map plus a `[key, value]` tuple per entry, and replacing a value no longer allocates. Iteration order, `forEachSafe` semantics and `values()` are unchanged; `entries()` now yields fresh `[key, value]` pairs rather than the map's internal tuples. About 9% off the sector-tick benchmark's mean tick. Trade-off: a fresh process that creates tens of thousands of long-lived entities in bulk and then destroys them can be slower, because V8 cannot pretenure the new arrays the way it pretenured the per-entry tuples; see [Benchmarks](../bench/README.md#known-trade-off-bulk-create-and-destroy).
- [vecs]: Queries, systems, entities, component metadata and worlds now create every internal field in their constructors instead of adding some on first use, so all instances of a class share one V8 hidden class and the per-tick paths (`System._run`, `Entity.set`, routing) stop doing megamorphic property loads. No behavior change; about 11% off the sector-tick benchmark's mean tick.
- [vecs]: A component update no longer walks the component's term consumers when none of them can react: terms count the consumers that act on data refreshes outside an in-flight membership event, and skip the walk when that count is zero and no event is in flight. Consumers that implement `onTermRefresh` through `Term.subscribe` are always counted. About 3% off the sector-tick benchmark's mean tick.
- [repo]: `npm run bench:vecs` (the `@vworlds/vecs` `bench:ecs` script) runs again under Vitest 4, which rejects the removed `--poolOptions` flag. The script now uses `--maxWorkers=1` and pins the default reporter, so the results also print when Vitest detects an AI agent and would otherwise pick its quiet reporter.
