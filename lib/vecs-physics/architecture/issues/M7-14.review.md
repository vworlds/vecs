# M7-14 — Post-M7 dead code sweep

**Phase:** Post-M7 cleanup.
**Depends on:** M7-11 (end of M7).

## Goal

Find and delete code that became dead during the M7 migration but was
preserved by mistake. M7-10 explicitly listed a "survivors" set in its
AC, but in at least one case the survival rationale was stale by the
time M7-10 ran. There are likely others.

## Background

The M7 migration moved `vecs-physics` from a TS-engine implementation
to a `box2d3-wasm` wrapper across 11 tickets, with many systems
rewritten in parallel. Each ticket's coder respected the strict Files
touched contract and didn't sweep beyond its scope. As a result, when
M7-10 (the engine purge) ran, it relied on the M7-10 ticket's list of
files to delete vs. preserve — and that list was written before the
parallel band committed.

**Concrete example surfaced after M7-11:**
`lib/vecs-physics/src/math/vec2.ts` was retained per M7-10 AC #2:

> Survivors confirmed in place: `lib/vecs-physics/src/math/vec2.ts` —
> public `Vec2` type.

By the time M7-10 ran, the public `Vec2` type lived in
`src/components/geometry.ts:6` (defined inline) and was re-exported
from `src/index.ts:26` via the geometry path. The `math/vec2.ts` file
has:

- **Zero importers** anywhere in `src/` or `tests/` —
  `grep -rn 'from.*math/vec2' lib/vecs-physics/src lib/vecs-physics/tests`
  returns nothing.
- A duplicate `Vec2` interface that nothing reads.
- 25+ pure functions (`add`, `sub`, `dot`, `cross`, `normalize`,
  `length`, …) and a `ZERO` constant, all unused.

M7-10's Sonnet subagent took the survival reason literally and didn't
verify the rationale still held. The whole file is orphan.

Probably more like this exists. This ticket is a systematic sweep.

## Approach

1. **Tooling.** Try `npx knip` (or `ts-unused-exports`) on
   `lib/vecs-physics`. Both can find unreferenced exports and orphan
   files. If neither is available without install, fall back to
   manual `grep -rn 'from.*"<path>"'` for each module in `src/`.
   Whatever tool you use, **verify** every flagged result
   manually — tools have false positives on barrel re-exports and
   conditional imports.

2. **Known starting point.**
   - `lib/vecs-physics/src/math/vec2.ts` — confirmed orphan; delete.

3. **Likely suspects (verify, don't assume).**
   - Other files in `src/math/` that weren't in M7-10's deletion
     list. M7-10 deleted `aabb.ts`, `rot.ts`, `transform.ts`,
     `constants.ts`. The only survivor was `vec2.ts`. After
     deleting `vec2.ts` the whole `src/math/` directory should be
     empty — delete it.
   - `src/util/warn.ts` — `WarnDedupe` is used by `debug.ts` and
     `mass_recompute.ts` (until M7-12 consolidates). Keep unless
     M7-12 has landed and removed the last consumer.
   - `src/util/resolve_body.ts` — extracted in M7-10 to share between
     `forces.ts` and `impulse_accumulate.ts`. Verify both still
     import it. If M7-13 simplifies pose_sync_out's resolution path,
     the linear-scan portion of this helper may go away.
   - `src/components/*` — any component file or exported symbol that
     nothing in `src/systems/` or `src/adapter/` references.
   - Adapter symbols that M7-10's `EnginePhysicsState` inheritance
     drop pulled in but nothing actually consumes. M7-10's closing
     report listed the inlined fields; reconcile against grep.
   - Anything in `src/index.ts`'s re-export list that no consumer
     imports. Use `tests/api/exports.test.ts` as the contract: if a
     symbol is in `tests/api/exports.approved.json` it stays
     (public surface); if it's exported by `index.ts` but not in the
     approved list, it shouldn't be exported at all — investigate.

4. **For each confirmed orphan:** delete the file (or the unused
   export). Run the verification gates after each deletion to catch
   cascades.

5. **Don't refactor surviving code.** This is a deletion ticket. If
   you find a smell while in there, log it for a future ticket
   rather than mixing it into this commit.

## Acceptance criteria

1. `lib/vecs-physics/src/math/vec2.ts` deleted. If that empties
   `src/math/`, delete the directory.
2. All confirmed dead files/symbols surfaced by the sweep are
   deleted. Each one is named in the closing report with the path
   and the evidence-of-deadness (zero importers, etc.).
3. `tests/api/exports.test.ts` still passes — the public surface
   contract is unchanged.
4. `npm run typecheck && npm run lint && npm run test` pass.
5. `npm run examples` passes — the four examples still bootstrap.
6. `npm run bench` runs.
7. The closing report includes any deletion candidates that turned
   out to be false positives (used by tooling, indirectly re-exported,
   etc.) with the reason they survived.

## Files touched

**Deleted:** at least `lib/vecs-physics/src/math/vec2.ts`. Other
files identified during the sweep.

**Modified:** possibly `lib/vecs-physics/src/index.ts` if the deleted
exports need pruning from the re-export list. (Probably not — the
known case re-exports `Vec2` from `components/geometry.ts`, not
`math/vec2.ts`.)

- `scripts/api-snapshot-lib.ts` — drop the `export` keyword from any
  helper that's only used inside the same file (e.g.
  `parseTypeExports`). This is in-scope for a dead-symbol sweep; the
  ticket originally only mentioned production files but the same
  principle applies to internal tooling.

## Notes

- The `math/vec2.ts` finding was the trigger for this ticket. It's
  worth a small commit on its own even if the broader sweep finds
  nothing else.
- If the sweep finds dead code that's load-bearing for a planned
  but un-shipped feature (e.g. M7-13 might want some of the deleted
  helpers), confirm with the user before deleting. When in doubt,
  defer.
- Tooling note: `knip` typically catches more than `ts-unused-exports`
  but is also noisier. Both will misreport on type-only exports the
  exports test pins. Manual verification per candidate is mandatory.
