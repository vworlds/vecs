# M7-4 — Pose sync (in/out) + step on box2d3-wasm

**Phase:** Critical path (sequential). End of the non-runnable window.
**Depends on:** M7-3.

## Goal

Wire pose/velocity user→engine writes, the `b2World_Step` call, and the
engine→user write-back via `b2World_GetBodyEvents().moveEvents`. After
this ticket the branch is runnable: a falling box under gravity actually
lands.

## Acceptance criteria

1. `src/systems/pose_sync_in.ts` is rewritten as `PhysicsPoseSyncIn`:
   - **Silencing:** `ignoreSource([PhysicsSystemTag])` so write-backs
     from `PhysicsPoseSyncOut` (a tagged physics system) are filtered.
     Entry-time initialization is **not** silenced — bodies still
     initialize through a tagged source. (Behaviour confirmed in
     `tests/lifecycle/ignore_source.test.ts`.)
   - **`.update(Position, …)`** → `b2Body_SetTransform(bodyId, pos,
currentRotation)`.
   - **`.update(Rotation, …)`** → `b2Body_SetTransform(bodyId, currentPos,
b2MakeRot(angle))`.
   - **`.update(LinearVelocity, …)`** → `b2Body_SetLinearVelocity(bodyId,
vec)`.
   - **`.update(AngularVelocity, …)`** → `b2Body_SetAngularVelocity(bodyId,
value)`.
2. `src/systems/step.ts` is rewritten as `PhysicsStep` (phase
   `physics-step`):
   ```ts
   .run((_now, delta) => {
     const state = getPhysics(world);
     if (state.debug && Math.abs(delta / 1000 - state.fixedTimeStep) > 1e-4) {
       warn.warnOnce(0, "delta-mismatch", ...);
     }
     b2World_Step(state.worldId, state.fixedTimeStep, state.subSteps);
   });
   ```
3. `src/systems/pose_sync_out.ts` is rewritten as `PhysicsPoseSyncOut`
   (phase `physics-post`):
   - Read `b2World_GetBodyEvents(worldId).moveEvents` after the step.
   - For each move event, resolve `b2BodyId → Entity` via
     `state.entityByBody`:
     - `entity.set(Position, { x, y })`
     - If the entity has `Rotation`: `entity.set(Rotation, { angle })`
     - If the entity has `LinearVelocity` / `AngularVelocity`: write
       those too.
   - **Only dynamic bodies are written back.** Kinematic and static
     poses are user-owned and never overwritten.
   - Every `entity.set(...)` here is sourced by this tagged physics
     system so `PhysicsPoseSyncIn`'s `ignoreSource` filter drops them
     next frame.
4. `src/engine/step.ts`, `src/engine/solver.ts`, `src/engine/collide.ts`,
   `src/engine/island.ts`, all of `src/engine/manifold/`,
   `src/engine/narrow_phase.ts`, `src/engine/distance.ts`,
   `src/engine/ccd.ts` are **stubbed**, not deleted (same pattern M7-2
   applied to `engine/body.ts` / `engine/solver_set.ts` and M7-3 applied
   to `engine/shape.ts` / `engine/geometry.ts` / `engine/dynamic_tree.ts`
   / `engine/broad_phase.ts`). M7-4's only requirement is that the **new**
   WASM step (`b2World_Step`) and pose-sync paths do not reach into the
   legacy step/collide/island/manifold/ccd surface. The stubs may retain
   whatever symbols the surviving engine internals (`engine/sleep.ts`
   still calls into island/contact bookkeeping; `engine/state.ts` and
   `engine/contact.ts` reach into solver/island internals) and surviving
   engine tests still import. Full deletion lands in M7-10.
   - **Strict no-go list** (M7-4's actual contract): nothing under
     `src/adapter/`, `src/install.ts`, the rewritten
     `src/systems/pose_sync_in.ts`, `src/systems/pose_sync_out.ts`, or
     `src/systems/step.ts` may import from these stubs. Other
     `src/systems/*` files (forces, kinematic, mass_recompute,
     material_filter_sync, lifecycle, shape_lifecycle, shape_pose_sync —
     the last three are already clean from M7-2/M7-3) may continue
     importing from them until their owning ticket rewrites them.
     `src/install.ts` may continue to import `installSleepHooks` from
     `engine/sleep.ts` (this is not one of the stubbed files), which in
     turn reaches into island/contact bookkeeping inside the stubs —
     that transitive use is acceptable.
   - Add a one-line file header on each: "Transitional stub kept alive
     for surviving engine code; full deletion happens in M7-10."
   - The stub does not need to strip the _bodies_ of retained helpers
     — leaving the legacy step/solver/collide/island/manifold/ccd
     internals intact for engine tests is fine. They are no longer
     reachable from the WASM-driven runtime path; nothing calls into
     them from production now that `PhysicsStep` invokes `b2World_Step`
     instead of `engineStep`.
   - If trimming leaves surviving engine internals referencing dropped
     symbols, restore the export rather than silently widening into
     other engine files. If a symbol genuinely can't be supported in
     the stub, surface it in the closing report.
5. After this ticket: `cd lib/vecs-physics && npm run test` runs to
   completion. Some tests outside the four critical-path systems may
   still fail (the parallel-band systems M7-5..M7-9 are not yet
   rewritten); the critical-path tests listed below must pass.

## box2d3-wasm calls

**`PhysicsPoseSyncIn`:**

- `b2Body_SetTransform(bodyId, pos, rot)`
- `b2Body_SetLinearVelocity(bodyId, vec)`
- `b2Body_SetAngularVelocity(bodyId, value)`
- `b2MakeRot(angle)` (allocates; `.delete()` after the set call)
- Reusable `b2Vec2` pooled at state level for position/velocity sets
  to avoid per-call allocation (PLAN.md § **Memory management**).

**`PhysicsStep`:**

- `b2World_Step(worldId, timeStep, subStepCount)` — single call per
  step.

**`PhysicsPoseSyncOut`:**

- `b2World_GetBodyEvents(worldId)` — read once, walk `moveEvents`.
  (The same events array also carries `hitEvents`, which M7-8 consumes
  — for now just iterate `moveEvents`.)

Cross-reference: PLAN.md Part 1 § **PhysicsPoseSyncIn**, §
**PhysicsStep**, § **PhysicsPoseSyncOut**, § **Pose and velocity
synchronization**.

## Carryovers from M7-3

M7-3 review surfaced four points the M7-4 coder must honour. They
refine, not override, the acceptance criteria above:

- **Body transform vs shape recreate.** The M7-3 reviewer suggested
  `pose_sync_in.ts` should call `recreateShapeForEntity` when the body
  moves "because the shape's world-space pose changes implicitly". We
  do **not** believe this is correct: `b2Body_SetTransform(bodyId, …)`
  updates the body transform and Box2D automatically refreshes every
  attached shape's world-space pose plus its broad-phase proxy AABB
  (this is core Box2D behaviour — shapes are attached to bodies and
  follow the body transform; the local pose `ShapePosition` /
  `ShapeRotation` is what M7-3's `PhysicsShapePoseSync` handles via
  destroy + recreate). Verify by reading the box2d3-wasm typings (or
  the upstream `box2d/src/body.c::b2Body_SetTransform`) and adding a
  test that moves a body and asserts the attached shape's contact
  detection updates without an explicit recreate. If the reading
  agrees, do **not** call `recreateShapeForEntity` from any pose-sync
  path. If you find evidence the reviewer was right, surface it in the
  closing report rather than silently adding the recreate.
- **Route the step's delta-mismatch warning through the debug system.**
  M7-3 must-fix established that validation/diagnostic warnings flow
  through the deduped debug system (`debug.ts` owns `WarnDedupe`), not
  through raw `console.warn` or per-system warn helpers. The
  `delta-mismatch` warning in `PhysicsStep` (AC #2) should either use
  the existing `warn.warnOnce(0, "delta-mismatch", …)` if that helper
  is already wired through `WarnDedupe`, or use the debug system's
  emission path directly. Do not introduce a fresh undeduped warn.
- **API-existence check for every b2 setter you use.** Before committing
  to runtime calls in `pose_sync_in.ts`, confirm `b2Body_SetTransform`,
  `b2Body_SetLinearVelocity`, `b2Body_SetAngularVelocity`, and
  `b2MakeRot` actually exist in `box2d3-wasm@5.2.0`. M7-2 discovered
  `b2Body_SetAllowFastRotation` was missing despite being in PLAN.md.
  If anything you need is missing, fall back to a documented
  alternative (e.g. `b2Body_SetTransform` covers both position and
  rotation when one comes in alone — use a getter for the other axis)
  and flag a PLAN.md Part 1 docs fix in the closing report. Do not
  ship a runtime-feature-detect wrapper.
- **Performance: pool the `b2Vec2` on `PhysicsState`, not per-system.**
  Per the ticket notes and PLAN.md § _Memory management_, the
  reusable `b2Vec2` for position/velocity sets lives on the adapter
  `PhysicsState` (one instance, reused by all four pose-sync setters
  in `pose_sync_in.ts`). Allocate it in the `PhysicsState` constructor
  alongside the maps M7-1 introduced; release via `withAllocated`
  semantics is not appropriate here because the lifetime is the
  world's, not a single call. Add a property like
  `state.scratchVec2: b2Vec2` and clean it up in the (currently
  non-existent) world dispose path or simply leave it for the GC at
  process exit. Document the choice in code.

## Notes

- `b2MakeRot` allocates; do not skip the `.delete()` in `PoseSyncIn`'s
  rotation path.
- The `moveEvents` walk dominates per-frame allocation pressure.
  Resolve `b2BodyId → Entity` via the existing `state.entityByBody` map;
  do not allocate intermediate arrays.
- `PhysicsPoseSyncOut` must NOT write back to kinematic or static
  bodies even if `moveEvents` reports them moving — those poses are
  user-owned. Check `state.bodyTypeByEntity` (or call
  `b2Body_GetType`) before each set.
- Branch is runnable end-to-end after this ticket lands.
