# M7-7 — Material, filter, sensor, and mass recompute on box2d3-wasm

**Phase:** Parallel band (after M7-4).
**Depends on:** M7-3 (shape ids exist and look up).
**Parallel with:** M7-5, M7-6, M7-8, M7-9.

## Goal

Wire shape-side property updates (`Material`, `CollisionFilter`,
`Sensor`) and body mass recompute to box2d3-wasm setters and the
auto-mass behaviour of `b2Shape_SetDensity`.

## Acceptance criteria

1. `src/systems/material_filter_sync.ts` is rewritten as
   `PhysicsMaterialFilterSync` (phase `physics-pre`):
   - **`.update(Material, …)`** on a shape entity:
     - `density` → `b2Shape_SetDensity(shapeId, density, true)`
       (the `true` flag triggers auto mass-recompute on the parent
       body — covers most of M7-7's mass needs).
     - `friction` → `b2Shape_SetFriction(shapeId, value)`
     - `restitution` → `b2Shape_SetRestitution(shapeId, value)`
     - `rollingResistance` → `b2Shape_SetRollingResistance(shapeId, value)`
     - `tangentSpeed` → corresponding setter.
     - `userMaterialId` → corresponding setter (or recreate if no setter
       is exposed; document which it is in the implementation).
   - **`.update(CollisionFilter, …)`**:
     - Build a `b2Filter` from `categoryBits` (32 bits zero-padded to
       Box2D's 64 bits — see PLAN.md § **Settled decisions**),
       `maskBits` (same widening), `groupIndex`.
     - Call `b2Shape_SetFilter(shapeId, filter)`. Box2D rebuilds the
       affected contacts internally on the next step.
     - `.delete()` the filter object after the set call.
   - **`.update(Sensor, …)`**: v1 implementation is **destroy +
     recreate** the shape with `def.isSensor = true/false`. No runtime
     setter. Coordinate with `PhysicsShapeLifecycle`'s recreate path so
     this does not double-fire.
2. `src/systems/mass_recompute.ts` is rewritten as
   `PhysicsMassRecompute` (phase `physics-pre`):
   - Most cases are no-ops post-M7 because `b2Shape_SetDensity(..., true)`
     auto-recomputes mass.
   - For bodies explicitly marked dirty in `state.dirtyMassBodies` (e.g.
     after a manual flag flip set elsewhere), call
     `b2Body_ApplyMassFromShapes(bodyId)` and clear the dirty set.
3. `dynamic-body-without-density` debug code (PLAN.md debug table) is
   emitted from this system after recompute when a dynamic body's total
   mass is `0`. The body does **not** fall (Box2D keeps `mass = 0,
invMass = 0` for dynamic bodies with no positive-density shapes —
   PLAN.md § **Settled decisions**). Do not auto-fix; debug warn only.
4. `src/engine/mass.ts` is **stubbed**, not deleted (same pattern M7-2..
   M7-4 applied to engine files). The mass-recompute surface used by
   the new WASM path (`PhysicsMassRecompute` reading
   `state.dirtyMassBodies` and calling `b2Body_ApplyMassFromShapes`)
   does not reach into `engine/mass.ts`. The stub may retain whatever
   symbols surviving engine internals and engine tests still import.
   Strict no-go list: nothing under `src/adapter/`, `src/install.ts`,
   the rewritten `src/systems/material_filter_sync.ts`, or the
   rewritten `src/systems/mass_recompute.ts` may import from the stub.
   Other systems may continue to import from it until their owning
   ticket rewrites them. Full deletion lands in M7-10. Add a one-line
   header: "Transitional stub kept alive for surviving engine code;
   full deletion happens in M7-10."

  is the key flag.

## Notes

- 32→64-bit filter widening: only the lower 32 bits are populated; upper
  32 are zero. Document this in a code comment in
  `material_filter_sync.ts` because it's the only place in the codebase
  that crosses the width boundary.
- `Sensor` mass behaviour: sensors contribute to mass/CoM/inertia like
  solid shapes unless `density === 0` (PLAN.md § **Settled decisions**).
  Do not special-case sensor density.

**Findings:**

- **(must-fix) Chain shape Material/CollisionFilter updates silently skip WASM side** — `material_filter_sync.ts:30-35` (Material) and `material_filter_sync.ts:40-53` (CollisionFilter) only look up `state.shapeByEntityWasm` for WASM shape IDs. Chain entities are stored in `state.chainByEntity` (b2ChainId), not `shapeByEntityWasm`, so `shapeId` is always `undefined` for chains. Density, friction, restitution, and CollisionFilter changes on chain shapes are only applied to the legacy engine records (`applyLegacyMaterial` at line 37, `applyLegacyFilter` at line 56), leaving the WASM chain segments stale. Since `b2ChainId` has no per-segment material/filter setters in box2d3-wasm@5.2.0, the correct path is `recreateShapeForEntity`, which the `requiresMaterialRecreate` guard already triggers for rollingResistance/tangentSpeed/userMaterialId changes (via `readLegacyMaterial` which handles chains). The fix: in the Material handler, after the `shapeId !== undefined` block, add a `state.chainByEntity.has(entity.eid)` guard that calls `recreateShapeForEntity(state, entity)`. Same for the CollisionFilter handler. This ensures ALL material/filter changes on chain entities are applied correctly, not just the "requiresMaterialRecreate" subset.

- **(should-fix) `syncLegacyMassState` is O(n) per frame even when no legacy bodies are dirty** — `mass_recompute.ts:32` iterates all `state.bodies.records` every frame. The per-item cost is low (a few property reads), but in worlds with hundreds of bodies, the cumulative cost is measurable. Acceptable as transitional code that will be deleted in M7-10, but worth noting for the implementer of M7-10 to verify this won't regress mid-migration.

- **(nit) Duplicate `dynamic-body-without-density` warn infrastructure** — `mass_recompute.ts:10` creates a second `WarnDedupe` instance scoped to `installMassRecompute`, separate from the one in `debug.ts:60`. Both emit the same debug code. `WarnDedupe` de-duplicates by `(eid, code)`, so no double-warning at runtime, but the infrastructure duplication is unnecessary. M7-10 should consolidate these into a single dedup source.

- \*\*(nit) Commit `85f7428` subject line is `feat: migrate material filter mass sync to wasm` — it exceeds the recommended ~50-char length and should carry a conventional-commit type prefix. The body is well-written and descriptive. Per `.agent/rules/commits.md`, the subject should be "concise, descriptive." This isn't a blocker but should tighten in future tickets.
