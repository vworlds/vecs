# M7-6 — Kinematic targets on box2d3-wasm

**Phase:** Parallel band (after M7-4).
**Depends on:** M7-2.
**Parallel with:** M7-5, M7-7, M7-8, M7-9.

## Goal

Rewrite the kinematic-target driver so kinematic bodies move toward
`KinematicTargetPosition` / `KinematicTargetRotation` via per-frame
velocity computation on box2d3-wasm.

## Acceptance criteria

1. `src/systems/kinematic.ts` is rewritten as `PhysicsKinematicTargets`
   (phase `physics-pre`).
2. For each entity with `Body.type === "kinematic"` and a
   `KinematicTargetPosition`:
   ```ts
   const pos = entity.get(Position);
   const tpos = entity.get(KinematicTargetPosition);
   const dx = tpos.x - pos.x,
     dy = tpos.y - pos.y;
   const dist = Math.hypot(dx, dy);
   if (dist > tpos.tolerance) {
     let vx = dx / dt,
       vy = dy / dt;
     // Clamp to maximumLinearSpeed (resolved option).
     const sp = Math.hypot(vx, vy);
     if (sp > state.maximumLinearSpeed) {
       const s = state.maximumLinearSpeed / sp;
       vx *= s;
       vy *= s;
     }
     b2Body_SetLinearVelocity(bodyId, { x: vx, y: vy });
     if (tpos.wake) b2Body_SetAwake(bodyId, true);
   } else {
     b2Body_SetLinearVelocity(bodyId, { x: 0, y: 0 });
     // Target stays attached; user updating the component re-engages.
   }
   ```
3. Rotation handled the same way using shortest-arc:
   `let da = wrap(tang.angle - rot.angle, -PI, PI);` →
   `b2Body_SetAngularVelocity(bodyId, da / dt)`; zero velocity inside
   tolerance.
4. Non-kinematic bodies that carry a target component are ignored.
   Debug system emits a warning (existing debug code; this ticket just
   has to make sure the path doesn't crash on dynamic bodies).
5. `dt` is the resolved `fixedTimeStep` from options (not the Vecs
   `delta`).

## box2d3-wasm calls

- `b2Body_GetType(bodyId)` (or cached `state.bodyTypeByEntity`) — filter
  for kinematic bodies.
- `b2Body_SetLinearVelocity(bodyId, vec)` — drive toward
  `KinematicTargetPosition`; pool `b2Vec2`.
- `b2Body_SetAngularVelocity(bodyId, value)` — drive toward
  `KinematicTargetRotation`.
- `b2Body_SetAwake(bodyId, true)` — when `wake` is set on the target
  component and we just commanded motion.

Cross-reference: PLAN.md Part 1 § **PhysicsKinematicTargets** and §
**Kinematic target handling**.

## Carryovers from M7-1..M7-4

The critical-path tickets established four patterns that apply here:

- **Read from the WASM-suffixed maps.** Body lookups use
  `state.bodyByEntityWasm` (eid → `b2BodyId`) / `state.entityByBody`.
  The legacy `state.bodyByEntity` holds engine handles, not
  `b2BodyId`s; do not read from it. M7-10 deletes it.
- **`bodyTypeByEntity` cache vs `b2Body_GetType`.** The ticket's box2d3
  -wasm-calls section suggests either `b2Body_GetType(bodyId)` (per
  call) or a cached `state.bodyTypeByEntity` (does not currently exist
  on the adapter `PhysicsState`). Pick `b2Body_GetType` for simplicity
  unless profiling shows it dominates the kinematic-targets path —
  there typically aren't many kinematic bodies, and the call is cheap.
  If you choose to add the cache, **list `src/adapter/state.ts` under
  Files touched** before starting (M7-4 hit this exact gate by not
  pre-amending Files touched), and populate it from
  `PhysicsBodyLifecycle.enter` / `.update(Body, …)` — which means M7-2's
  `lifecycle.ts` would also need to go into Files touched. State your
  choice in the closing report.
- **Verify each box2d3-wasm setter exists in v5.2.0 before committing.**
  Confirm `b2Body_GetType`, `b2Body_SetLinearVelocity`,
  `b2Body_SetAngularVelocity`, and `b2Body_SetAwake` exist before
  writing the calls. M7-2 discovered `b2Body_SetAllowFastRotation`
  missing; this discipline is non-negotiable. Flag any mismatch in the
  closing report as a PLAN.md docs fix.
- **Pool the `b2Vec2`, don't allocate per call.** M7-4 added
  `state.scratchVec2: b2Vec2` on the adapter `PhysicsState`. Reuse it
  for `b2Body_SetLinearVelocity` — both the active-motion branch and
  the zero-velocity-inside-tolerance branch. Do not allocate a fresh
  `{ x, y }` object per kinematic body per step. (`b2Body_SetAngular
Velocity` takes a plain `number`, no allocation.)
- **Warnings through the debug system.** The dynamic-body-carrying-a
  -kinematic-target warning (PLAN.md debug table) routes via the debug
  system's `WarnDedupe`, not raw `console.warn`. Read
  `src/systems/debug.ts` first to see if the warn is already produced
  there for the same condition.

## Notes

- Targets are **left attached** after reaching the goal. The user
  updates the component to re-engage. Do not remove the component on
  arrival — that would create archetype churn.
- `tolerance` defaults: `0.001` for both position and rotation
  (PLAN.md defaults table).

**Notes for the next ticket:** The kinematic system reads body position/rotation from WASM (not ECS components). This means `Position` / `Rotation` component writes by user code between steps won't affect kinematic targeting — the system reads the engine's last-integrated pose. This is the contract (and matches the old TS engine's `BodySim` reads), but it means a user who sets both a new `Position` and a `KinematicTargetPosition` in the same frame won't see the new position reflected in the target computation until the next frame. Document this if it's surprising.
