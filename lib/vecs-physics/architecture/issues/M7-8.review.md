# M7-8 — Contact / sensor / hit events on box2d3-wasm

**Phase:** Parallel band (after M7-4).
**Depends on:** M7-3 (shape ids exist) and M7-4 (`b2World_Step` runs).
**Parallel with:** M7-5, M7-6, M7-7, M7-9.

## Goal

Wire opt-in flag synchronization and the post-step event publish path
for `ContactEvents`, `SensorEvents`, and `HitEvents`.

## Acceptance criteria

1. `src/systems/event_opt_in_sync.ts` is rewritten as
   `PhysicsEventOptInSync` — hook-driven (PLAN.md Part 1 §
   **PhysicsEventOptInSync**):
   - On `ContactEvents` added to a shape entity →
     `b2Shape_EnableContactEvents(shapeId, true)`.
   - On `ContactEvents` removed → `b2Shape_EnableContactEvents(shapeId,
false)`.
   - Same wiring for `HitEvents` → `b2Shape_EnableHitEvents(shapeId,
bool)`.
   - Same wiring for `SensorEvents` → `b2Shape_EnableSensorEvents(shapeId,
bool)`.
   - Implement via component lifecycle hooks (`onAdd`/`onRemove`) on
     the three event components, registered from `installPhysics`. The
     phase entity for this system carries `PhysicsSystemTag` (in case
     downstream silencing wants it).
2. `src/systems/events.ts` is rewritten as `PhysicsEvents`
   (phase `physics-post`):

   ```ts
   const worldId = state.worldId;
   const ce = b2World_GetContactEvents(worldId);
   const se = b2World_GetSensorEvents(worldId);
   const be = b2World_GetBodyEvents(worldId); // moveEvents consumed by PoseSyncOut; we read hitEvents here
   ```

   - Walk `ce.beginEvents` / `ce.endEvents`; resolve each `b2ShapeId` to
     `Entity` via `state.entityByShape`. If the entity has been
     destroyed (Vecs `_destroyed`) drop silently — events still flow to
     the **other** shape's component (PLAN.md § **Entity-reference
     safety**). Push into the receiving entity's `ContactEvents.begin` /
     `ContactEvents.end`.
   - Walk `se.beginEvents` / `se.endEvents`; same pattern for
     `SensorEvents`.
   - Walk `be.hitEvents`; same pattern for `HitEvents`.
   - Call `world.entity(eid).modified(ContactEvents)` (et al.) **once
     per receiving entity per step**.
   - **Silent clear semantics:** for shapes that received events last
     step but not this step, mutate `events.begin.length = 0;
events.end.length = 0;` without calling `modified()`. Track three
     independent `previouslyTouched` sets — one per event component
     type — on `PhysicsState`.
   - Arrays are owned by the user's component instance; we mutate
     length, never reassign the array reference (PLAN.md § **Events
     pipeline**).

3. `src/engine/sensor.ts` is **stubbed**, not deleted (same pattern M7-2..
   M7-4 applied to engine files). M7-8's only requirement is that the
   new WASM event path (`PhysicsEvents` and `PhysicsEventOptInSync`)
   does not reach into `engine/sensor.ts`. The stub may retain whatever
   symbols surviving engine internals and engine tests still import.
   Strict no-go list: nothing under `src/adapter/`, `src/install.ts`,
   the rewritten `src/systems/event_opt_in_sync.ts`, or the rewritten
   `src/systems/events.ts` may import from the stub. Other systems may
   continue to import from it until their owning ticket rewrites them.
   Full deletion lands in M7-10. Add a one-line header: "Transitional
   stub kept alive for surviving engine code; full deletion happens in
   M7-10."
4. Event payload carries the **other shape entity**
   (`ContactEvent.other`, etc.), resolved from `b2ShapeId` at publish
   time. If the other shape's entity is destroyed, drop the event
   silently — do not emit a half-populated payload.

## Carryovers from M7-1..M7-4

The critical-path tickets established four patterns that apply here,
plus two M7-4-specific findings that hit M7-8 hardest of the band:

- **Read from the WASM-suffixed maps.** Shape lookups use
  `state.shapeByEntityWasm` (eid → `b2ShapeId`) and reverse via
  `state.entityByShape`. Body lookups use `state.bodyByEntityWasm` /
  `state.entityByBody`. Legacy engine maps will be removed in M7-10.
- **Route warnings through the debug system.** Any diagnostic warn for
  malformed event flow goes through `WarnDedupe`, not raw
  `console.warn`. Read `src/systems/debug.ts` first.

### M7-4 findings that directly hit M7-8

- **Event API shape is `.count` + `.GetEvent(i)`, not arrays.** M7-4
  confirmed that `b2World_GetBodyEvents(worldId)` in
  `box2d3-wasm@5.2.0` returns an object with `moveCount` and
  `GetMoveEvent(i)`, **not** a `moveEvents` array as PLAN.md and this
  ticket's pseudocode imply. The same pattern almost certainly applies
  to `b2World_GetContactEvents` (likely `beginCount` /
  `GetBeginEvent(i)` and `endCount` / `GetEndEvent(i)`) and
  `b2World_GetSensorEvents`. Read the runtime API (either the
  `box2d3-wasm` typings in `node_modules/box2d3-wasm` or by inspecting
  the returned object's properties at runtime in a quick test) and
  implement against the actual shape. Flag the PLAN.md Part 1 docs
  mismatch in the closing report — the contact/sensor APIs need the
  same correction M7-4 applied to body events.

- **`Map<b2ShapeId, EntityId>` direct lookup always misses under
  Emscripten.** M7-4 discovered that `state.entityByBody.get(bodyId)`
  always misses because each call to `event.bodyId` returns a fresh JS
  wrapper around the underlying Emscripten struct — `Map.get` uses
  reference identity, not struct equality. M7-4's `pose_sync_out.ts`
  works around this with a linear-scan fallback (O(N²) per step;
  flagged as a follow-up). For M7-8 the same will happen with every
  `b2ShapeId` resolution from contact/sensor/hit events — and event
  density is higher than body-move density, so O(N²) per step is more
  damaging. Pick one of:
  1. **Linear-scan fallback** (matches M7-4 pattern; simple but slow
     when many events fire per step). Acceptable for v1 if event
     density stays low; flag for the O(1) fix in your closing report.
  2. **Composite-string key map.** Maintain
     `state.entityByShapeKey: Map<string, EntityId>` keyed by
     `` `${shapeId.index1}:${shapeId.world0}:${shapeId.generation}` ``.
     Populate it from `PhysicsShapeLifecycle.enter` (M7-3's
     `src/systems/shape_lifecycle.ts`) and drop it in `.exit`.
     Lookups in `PhysicsEvents` build the same string and call
     `Map.get` — O(1) at the cost of one string concat per lookup. If
     you choose this, **list `src/adapter/state.ts` and
     `src/systems/shape_lifecycle.ts` under Files touched** before
     starting (M7-4 hit the strict-Files-touched gate by not
     pre-amending). Same for bodies if you also need
     `state.entityByBodyKey` for hit-event resolution.

  Whichever you pick, document the choice and the rationale in the
  closing report. If you pick option 2 and find that the M7-4
  `pose_sync_out.ts` linear-scan can be retired in the same pass,
  surface that as a should-fix in your closing report — don't widen
  scope to fix M7-4 inside this ticket unless trivial.

- **Shared `state.bodyEventsThisStep`.** AC's note says "Coordinate so
  the buffer is read once — both systems can call
  `b2World_GetBodyEvents` but a single read shared via
  `state.bodyEventsThisStep` is cleaner." Adding this state requires
  modifying `src/adapter/state.ts` (Files touched) and **reading from
  the cache in `src/systems/pose_sync_out.ts`** (M7-4's file, also
  Files touched). The cost-of-touch may exceed the benefit; reading
  `b2World_GetBodyEvents` twice is cheap (it reads from a WASM struct,
  doesn't regenerate events). Recommendation: **leave both reads
  independent for M7-8**; flag a follow-up if profiling later shows
  this dominates. State your choice in the closing report.

- **Verify each box2d3-wasm setter exists in v5.2.0 before committing.**
  Confirm `b2Shape_EnableContactEvents`, `b2Shape_EnableHitEvents`,
  `b2Shape_EnableSensorEvents`, `b2World_GetContactEvents`,
  `b2World_GetSensorEvents`, `b2World_GetBodyEvents` all exist. For any
  missing setter, fall back per the M7-3/M7-4 pattern and flag a PLAN.md
  docs fix.

## Notes

- The `previouslyTouched` tracking is the only stateful piece in the
  events publisher. Three independent sets — one per event component —
  because a shape can opt into any subset. Keep them on `PhysicsState`.
- A body destroyed during the same step still gets its `endEvents`
  correctly emitted to the **other** shape's `ContactEvents`, provided
  the other shape's entity is still alive (PLAN.md § **Entity-reference
  safety**). Verify with the existing teardown test in `tests/events/`
  or `tests/lifecycle/contact_teardown.test.ts`.
