# M7-15 — Replace Box2D id reverse Maps with ArrayMap

**Phase:** Post-M7 cleanup.
**Depends on:** M7-13 (Emscripten id-wrapper Map.get fix).

## Goal

Replace the `Map<number, EntityId>` reverse lookups introduced by
M7-13 with vecs' `ArrayMap<EntityId>` keyed by Box2D public id
`index1` fields.

The hot paths should become one property read plus one `ArrayMap.get`,
which is a sparse-array read internally:

```ts
const eid = state.entityByBodyIndex.get(event.bodyId.index1);
```

No hash lookup, no wrapper identity issue, no generation check.

## Background

M7-13 fixes the immediate correctness/perf bug caused by using
Emscripten wrapper objects as `Map` keys. It switches reverse lookups
from `Map<b2BodyId, EntityId>` / `Map<b2ShapeId, EntityId>` to
`Map<number, EntityId>` keyed by `.index1`.

That removes the O(N²) linear fallback, but the lookup is still a JS
hash-map operation in the highest-volume event paths:

- body move events in `pose_sync_out.ts`
- contact events in `events.ts`
- sensor events in `events.ts`
- hit events in `events.ts`
- destroyed-body impulse guards in `impulse_accumulate.ts`

Box2D ids are already small integer slots. Internally Box2D allocates
ids from an id pool and returns public ids with `index1 = internalId +
1` so `index1 === 0` can mean null. Freed ids are reused before new
ids are allocated. Reuse is LIFO, not lowest-free-id first, but the id
space remains bounded by the high-water number of Box2D objects created
in the world.

This makes vecs' `ArrayMap` keyed by public `index1` a better fit than
a built-in `Map`. `ArrayMap` keeps the familiar `.get/.set/.has/.delete`
API while backing it with a sparse JavaScript array. Slot `0` stays
unused/null-aligned. The backing array may have holes after destroy/reuse
churn; that is fine.

## Correctness invariant

Do **not** add generation checks in this ticket.

Instead, maintain the lifecycle invariant strictly:

- When a Box2D body is created, immediately write
  `state.entityByBodyIndex.set(bodyId.index1, eid)`.
- When that Box2D body is destroyed, delete the same slot before any
  future body can reuse the Box2D id.
- Same rule for shapes and `state.entityByShapeIndex`.

Box2D increments `generation` when it reuses an id slot, but this
adapter does not need to read it as long as stale entries are removed
on every Box2D destroy path. If a stale entry exists, that is a
lifecycle bug and should be fixed at the destroy site, not papered
over with generation checks in hot lookups.

`ArrayMap.get` returns `undefined` for empty slots. Test misses with
`eid === undefined`, not a truthiness check. `EntityId` is a numeric id
and future ECS changes should not make lookup correctness depend on
which numbers are truthy.

## Approach

1. Replace the M7-13 reverse maps on `PhysicsState`:
   `entityByBodyIndex: Map<number, EntityId>` becomes
   `entityByBodyIndex: ArrayMap<EntityId>`.
   `entityByShapeIndex: Map<number, EntityId>` becomes
   `entityByShapeIndex: ArrayMap<EntityId>`.
2. Keep the names `entityByBodyIndex` and `entityByShapeIndex` unless
   M7-13 landed different names. The suffix still describes the key:
   public Box2D `index1`.
3. Update body lifecycle enter/exit:
   `enter` calls `state.entityByBodyIndex.set(bodyId.index1, eid)`.
   `exit` calls `state.entityByBodyIndex.delete(bodyId.index1)`.
4. Update shape lifecycle enter/exit the same way for `shapeId.index1`.
5. Keep lookup call sites on `.get(id.index1)`, but now they resolve
   through `ArrayMap` instead of built-in `Map`.
6. Keep `.has(id.index1)` where a boolean guard is clearer, or use an
   explicit `get(...) !== undefined` check when the entity id is needed.
7. Update comments in `adapter/state.ts` to document:
   - why these are `ArrayMap`s keyed by Box2D public `index1`
   - why slot `0` is unused
   - why generation is intentionally not checked
   - the requirement to clear slots on every Box2D destroy path

Clear with `ArrayMap.delete`:

```ts
state.entityByBodyIndex.delete(bodyId.index1);
```

The important invariant is that lookups after destruction observe
`undefined` before Box2D can reuse the slot.

## Acceptance criteria

1. `PhysicsState` uses `ArrayMap` for reverse id lookup:
   `entityByBodyIndex: ArrayMap<EntityId>` and
   `entityByShapeIndex: ArrayMap<EntityId>`. No `Map<number, EntityId>`
   remains for these two reverse maps.
2. Body lifecycle writes the body slot on create and clears it on
   destroy using `bodyId.index1` directly via `ArrayMap.set` and
   `ArrayMap.delete`. No `index1 - 1` conversion: public slot `0`
   remains unused to mirror Box2D null ids.
3. Shape lifecycle writes and clears the shape slot using
   `shapeId.index1` directly via `ArrayMap.set` and `ArrayMap.delete`.
4. `pose_sync_out.ts` resolves move-event bodies with
   `state.entityByBodyIndex.get(event.bodyId.index1)` and handles
   `undefined` as the miss case.
5. `events.ts` resolves contact, sensor, and hit shapes with direct
   `ArrayMap.get` lookups and handles `undefined` as the miss case.
6. `impulse_accumulate.ts` replaces destroyed-body guards that used
   built-in `Map` with `ArrayMap.has(bodyId.index1)` or an explicit
   `ArrayMap.get(bodyId.index1) !== undefined` check.
7. No generation checks are added to these hot-path lookups. The code
   comment explains that correctness comes from clearing slots on
   Box2D destruction.
8. Tests cover id reuse: create a body/shape, destroy it, create a new
   one that reuses the same `index1`, and assert the reverse lookup
   points to the new entity and not the old one.
9. Tests cover missing destroyed entries: after destroy, the reverse
   `ArrayMap.get` reads as `undefined` before any replacement object is
   created.
10. Existing gates pass: `npm run typecheck`, `npm run lint`,
    `npm run test`, `npm run examples`, and `npm run bench`.

## Notes

- Box2D reuses freed ids immediately, but reuse order is LIFO rather
  than lowest-free-id first. This does not matter for `ArrayMap`
  lookup; it only means the backing array should be treated as
  sparse/high-water, not as a dense list of live objects.
- If a future feature introduces multiple simultaneous Box2D worlds in
  one `PhysicsState`, revisit this invariant. Today each installed
  physics world owns its own state object, so `index1` is sufficient
  within that state.
- If a stale entity is ever observed through one of these `ArrayMap`s,
  the fix is to find the missing lifecycle clear for the corresponding
  Box2D destroy path.
