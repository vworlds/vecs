# M7-13 — Emscripten id-wrapper Map.get fix (O(N²) → O(1))

**Phase:** Post-M7 cleanup.
**Depends on:** M7-2 (body lifecycle), M7-3 (shape lifecycle), M7-4
(pose sync), M7-8 (events) — all shipped.

## Goal

Eliminate the O(N²) linear-scan fallback in `pose_sync_out.ts` and
`events.ts` by switching `entityByBody` and `entityByShape` from
`Map<b2*Id, EntityId>` (wrapper-keyed; broken under Emscripten) to
`Map<number, EntityId>` keyed by `bodyId.index1` / `shapeId.index1`.

## Background

box2d3-wasm IDs (`b2BodyId`, `b2ShapeId`) are exposed as plain
TypeScript structs:

```ts
type b2BodyId = { index1: number; world0: number; generation: number };
type b2ShapeId = { index1: number; world0: number; generation: number };
```

Internally these wrap an Emscripten C++ struct. Every time JS code
reads an id field from a Box2D event or return (`event.bodyId`,
`event.shapeIdA`, `event.sensorShapeId`, etc.), Emscripten allocates
a **fresh** wrapper object pointing at the same underlying struct
values.

This breaks `Map<b2BodyId, EntityId>` and `Map<b2ShapeId, EntityId>`:
JS `Map` uses reference identity for object keys, so even though the
struct fields match, `map.get(event.bodyId)` looks up a fresh wrapper
that was never used as the `.set` key — it always misses.

Discovered during M7-4 review (`pose_sync_out.ts:resolveBodyEntityId`
falls back to a linear scan over `state.entityByBody` comparing
`(index1, world0, generation)` field-by-field for every move event)
and again during M7-8 review (`events.ts:resolveShapeEntity` does the
same against `state.entityByShape` for every contact/sensor/hit
event). For N entities producing events, that's O(N²) per step.

The fields on the wrapper are directly readable from JS — reading
`bodyId.index1` is a property access, not an Emscripten function
call. We don't need composite keys, userData, or any other workaround.
A `Map<number, EntityId>` keyed by `.index1` works directly.

### Why `index1` alone is sufficient

`b2BodyId.world0` is always `0` for a single-world setup (vecs-physics
uses one `b2WorldId` per `installPhysics` call).

`b2BodyId.generation` increments when Box2D recycles a freed slot.
The lifecycle invariant prevents stale lookups:

- `PhysicsBodyLifecycle.enter` runs before any events for the new
  body and `.set(bodyId.index1, eid)`.
- `PhysicsBodyLifecycle.exit` runs and `.delete(bodyId.index1)`
  before the next `.enter` can reuse the slot.
- Move events fire only for bodies alive at the end of the step
  (Box2D contract). The event's `.index1` always points at a slot
  whose map entry reflects the current occupant.

If at some future point we add belt-and-suspenders defence, pack
generation into the key: `(index1 << 12) | (generation & 0xfff)` —
no allocation, no Map type change. Document the lifecycle invariant
in a code comment so the next maintainer can choose.

### Why the impulse maps are NOT affected

`state.pendingLinearImpulse` and `state.pendingAngularImpulse` are
also typed `Map<b2BodyId, …>` but are **safe by invariant**:

- Both are populated only by hooks (`Impulse.onSet`,
  `AngularImpulse.onSet`) which resolve `bodyId =
state.bodyByEntityWasm.get(entity.eid)`. That returns the exact
  same stored wrapper instance every time — `Map` preserves the
  identity of stored values.
- Lookups within the same hook chain (`pendingLinearImpulse.get(bodyId)`
  followed by `.set(bodyId, …)`) use the same wrapper.
- The pre-step drain iterates entries (`for (const [bodyId, …] of
state.pendingLinearImpulse)`) — iteration returns stored keys, so
  no `.get` lookup happens.
- The drained `bodyId` is passed to
  `b2Body_ApplyLinearImpulseToCenter(bodyId, …)`. The WASM trampoline
  extracts the struct fields from the wrapper; reference identity
  isn't involved.

The wrapper-miss problem **only** bites when a wrapper used as a key
originates from a different source than the wrapper used to store
that key. The impulse hooks never see a wrapper from anywhere but
`bodyByEntityWasm`. Document this invariant in `adapter/state.ts`
next to the declarations so a future maintainer doesn't introduce a
miss accidentally (e.g. by adding an "apply impulse on contact" path
that resolves bodyId from a contact event).

## Approach

1. Rename `state.entityByBody: Map<b2BodyId, EntityId>` →
   `state.entityByBodyIndex: Map<number, EntityId>`.
2. Rename `state.entityByShape: Map<b2ShapeId, EntityId>` →
   `state.entityByShapeIndex: Map<number, EntityId>`.
3. Update `PhysicsBodyLifecycle.enter` to `.set(bodyId.index1, eid)`
   and `.exit` to `.delete(bodyId.index1)`. Same for
   `PhysicsShapeLifecycle.enter`/`.exit` with `shapeId.index1`.
4. Update `pose_sync_out.ts`: drop `resolveBodyEntityId`, look up
   `state.entityByBodyIndex.get(event.bodyId.index1)` directly.
5. Update `events.ts`: drop `resolveShapeEntity`, look up
   `state.entityByShapeIndex.get(event.shapeIdA.index1)` etc.
   directly. Covers contact `shapeIdA`/`shapeIdB`, hit
   `shapeIdA`/`shapeIdB`, and sensor `sensorShapeId`/`visitorShapeId`
   — they all share the same lookup pattern.
6. Add a code comment in `adapter/state.ts` documenting the
   safe-by-invariant rule for the impulse maps and the lifecycle
   invariant for the index maps.

If a helper file ends up cleaner than inlining `.index1` (e.g. for
documentation value), put it at `src/util/id_index.ts`:

```ts
export const bodyIndex = (id: b2BodyId) => id.index1;
export const shapeIndex = (id: b2ShapeId) => id.index1;
```

This is one-line, low-value abstraction. Inline if there are few
call sites; helper if there are many.

## Acceptance criteria

1. `state.entityByBodyIndex: Map<number, EntityId>` and
   `state.entityByShapeIndex: Map<number, EntityId>` on adapter
   `PhysicsState`. The old `entityByBody` / `entityByShape` maps
   are removed.
2. `PhysicsBodyLifecycle.enter`/`.exit` populate/drain
   `state.entityByBodyIndex` using `bodyId.index1`.
   `PhysicsShapeLifecycle.enter`/`.exit` do the same for
   `state.entityByShapeIndex`. (Chain lifecycle has no reverse map
   needed — chains don't produce events that need
   shape-id-to-entity resolution; double-check this assumption.)
3. `pose_sync_out.ts` uses
   `state.entityByBodyIndex.get(event.bodyId.index1)` for resolution.
   `resolveBodyEntityId` and its linear-scan fallback deleted.
4. `events.ts` uses
   `state.entityByShapeIndex.get(event.shapeIdA.index1)` (and
   `.shapeIdB`, `.sensorShapeId`, `.visitorShapeId` as appropriate)
   for resolution. `resolveShapeEntity` and its linear-scan fallback
   deleted.
5. A code comment in `adapter/state.ts` documents:
   - Why `entityByBodyIndex` / `entityByShapeIndex` are keyed by
     `.index1` (Emscripten wrapper miss; lifecycle invariant).
   - Why `pendingLinearImpulse` / `pendingAngularImpulse` remain
     `Map<b2BodyId, …>` (safe-by-invariant; wrappers originate from
     `bodyByEntityWasm` only).
6. All existing tests pass (`npm run typecheck`, `npm run lint`,
   `npm run test`, `npm run examples`).
7. A new microbench under `lib/vecs-physics/bench/` exercises a
   many-moving-bodies workload (e.g. 500 dynamic bodies in motion)
   and shows the speedup over the linear-scan implementation.
   Numbers go into the CHANGELOG.

## Notes

- This pattern generalises. Any **future** Box2D API that returns a
  `b2*Id` from a struct (raycast hits, overlap query callbacks,
  contact list traversal, joint queries) will need the same
  `index1`-keyed reverse map. M7-11 deferred raycasts/overlap queries
  to v2; when those land, the `entityByShapeIndex` map is ready.
  Document the pattern explicitly in `adapter/state.ts` so future
  contributors know to use it.
- The wrapper-miss problem **only** affects `Map<b2*Id, V>` where
  the lookup wrapper originates from a different source than the
  stored wrapper. Forward maps (`bodyByEntityWasm: Map<EntityId,
b2BodyId>`) are unaffected because they're keyed by number.
- The fields on `b2*Id` are public TypeScript properties; reading
  `.index1` does not allocate or call into WASM. The cost of a
  lookup is one property read plus one `Map.get` — strictly cheaper
  than the linear-scan fallback for N > 1.
